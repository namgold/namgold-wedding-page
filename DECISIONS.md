# Wedding site: decisions and status

Status as of 2026-11-16: frontend v1 and the backend are built and deployed (live at linhhy.namgold.com via `docker compose up -d --build`) but the content is still placeholder. The Go API (RSVP, guestbook, admin endpoints), the admin page, Turnstile and Telegram code exist. Turnstile is inactive until the owner does the dashboard steps below and fills `.env`; Telegram is live since 2026-11-21 (two bots, see "Telegram sending"). See `progress.md`.
Next: owner's real info, photos and the real URL slugs, dashboard setup, the 3G budget and the music/fonts decision, then artwork polish. Built and deployed 2026-11-16: the 3 place versions, the bank QR switch (off), the readability pass and nginx gzip (see "Built on owner requirements" below).

## Goal
Best possible UX for a personal wedding page (owner is a frontend/fullstack dev). Not a template-based or hosted-builder site.

## Decided
- **UX first (owner, 2026-11-16):** easy for every guest, young or elderly. When a design choice trades looks against readability or ease, readability wins.
- **Performance (owner, 2026-11-16):** page weight matters. JS, fonts and images as small as possible. Mobile first (about 90% of guests), desktop also supported. Design for 3G. The numeric budget is still open (below).
- **3 place versions (owner, 2026-11-16):** the 3 parties (groom's hometown, bride's hometown, the couple's home) each get their own page and URL. Only party info differs: date, venue, map link, timeline. Names, families, album, wishes, gift box and copy are shared.
- **Two QRs (owner, 2026-11-16):** the site QR on the invitation has 3 variations, one per place URL. The bank QR is optional and has an on/off switch. Details below.
- **Languages (2026-11-16):** Vietnamese (default) + English. Vietnamese at `/<slug>`, English at `/en/<slug>`.
- **Design source (2026-11-16, superseded same day):** first an original recreation. The owner then said the result drifted from the original (fonts, backgrounds) and asked for it to match `temp/origin/index.html` exactly, so the template's floral webp art and gift-box images were copied into `public/images/` (overrides "never the template's files"; licensing is unverified, owner's call). Also changed to match: countdown and scroll-reveal removed (the original has neither), rose is back to `#9D6D63` (below the earlier AA contrast fix), hero short names `groomShort`/`brideShort` and hero photos are placeholders, dress code is pink, beige, white (owner, 2026-11-16; black removed later), configured per place as `dressCode` in `places.ts`, keyless Google Maps embed replaces the vendor's API key, "Add to calendar" stays an .ics download.
- **Frontend:** Next.js **static export** (`output: 'export'`), TypeScript. No Node in production.
- **Backend:** separate small **Go** API (stdlib `net/http`) with **SQLite** (pure-Go driver, e.g. `modernc.org/sqlite`, no cgo). Rust was considered and rejected as overkill.
- **Serving:** nginx stays the front door. `/` serves the static export, `/api/*` proxies to the Go service. Same origin, so no CORS.
- **Compose services:** `frontend` (multi-stage: Node builds, nginx serves), `api` (Go + SQLite volume), `cloudflared`. Follow the parent `../CLAUDE.md` conventions.
- **RSVP:** custom-built form. **No Google Form embed** (bad UX).
- **No central page (owner, 2026-11-16):** there is no page that lists or links the 3 places. Whoever gets a URL opens that place directly and must not learn the other two exist. `/en` and `/index.html` return 404 (nginx); `/` serves the `/wedding` page since 2026-11-21 (see "Changes 2026-11-21"). Do not add a chooser, an "other parties" link, a sitemap, or any text naming another place. The 3 versions differ ONLY in date, venue and address, map link and timeline (owner, 2026-11-16; on 2026-11-21 the owner added per-place ceremony name, reception name, hall and dress code, still only wording and party info, see "Changes 2026-11-21"): no place label, title or other wording may differ or hint that variations exist (the cover shows no place name; the `Place` type has no place-name field). Place data lives in `src/content/places.ts`, imported only by the route pages, so it stays out of the shared browser bundle; the build output was grepped to confirm each place's details appear only in its own files. (Not hidden: the families' hometown addresses in the shared Families section, and the shared guestbook, by design.)
- **Invites (changed 2026-11-16, was "one QR for everyone"):** one site QR per place, 3 in total, each opening that place's URL (`https://linhhy.namgold.com/invitation`, `/ceremony`, `/wedding`). **No personalized links or tokens.** The RSVP form is open to anyone with the link.

## Built on proposed defaults (2026-11-16, owner said "continue", not explicitly confirmed; cheap to change)
- **RSVP fields:** name (60), side groom/bride, place (sent by the page, not asked), attending yes/no, guest count 1-10 (0 when declining), dietary (200), message (500).
- **Duplicates:** append-only. The latest response per (name, side, place), case-insensitive, wins; older rows are kept and shown greyed as "superseded". A guest invited to two parties can answer both. Admin totals count only the latest, overall and per place. Rows from before places existed have an empty place.
- **Per household vs per person:** one response per submission, with a guest count (so a household can submit once for everyone).
- **RSVPs notify Telegram:** yes (plain text, best effort).
- **Telegram message content (owner, 2026-11-21):** Vietnamese. Wish: name and wish. RSVP: name, side (Nhà gái / Nhà trai), which ceremony (place name, not the URL or slug; `/` and `/wedding` are one page and show the same name), attending with the number of people (or cannot attend). Wishes and RSVPs use separate bots and separate groups.
- **Moderation:** wishes are `enabled` on submit; the admin hides bad ones afterwards.
- **Admin UI:** `/admin` (static page, `noindex`, `no-store`) with Wishes (hide/show) and RSVPs (summary, list, CSV download). CSV cells starting with `= + - @` are prefixed with `'` against formula injection.
- **Turnstile site key** is served at runtime by `GET /api/config` (no rebuild needed to change it). The widget only renders when `TURNSTILE_SECRET` and `TURNSTILE_SITE_KEY` are both set.
- **Rate limit:** 10 submissions per 10 minutes per client IP, separately for wishes and RSVPs (keyed on `CF-Connecting-IP`; in memory, resets on restart; generous because guests share venue wifi).

## Changes 2026-11-22 (owner requests, in order)
- **Admin buttons showed the arrow cursor.** Tailwind v4 preflight no longer gives `<button>` a pointer cursor. One `@layer base` rule in `globals.css` covers enabled buttons, `[role=button]`, `summary` and `select` for the whole site; disabled buttons keep `not-allowed`.
- **Admin sorting and filter (owner, sketched for later infinite scroll).** The owner asked for Sorting (Date, Name, Status), Direction and Status (All, Hidden, Shown) on Wishes, default newest first, and said the list will get infinite scroll with virtualization, so the API had to be shaped for it. Decision: **offset/limit plus `total` and `counts`** instead of a cursor. Why: a virtual list sizes its scroll bar from `total` and must jump to any position (a cursor only walks forward), and name/status orders would need composite cursors. Every order ends in the unique id so pages never repeat or skip. `limit` defaults to and is capped at 1000, so an unpaged caller still works. Invalid values are 400 and only pick fixed SQL fragments.
- **My assumptions, not confirmed by the owner:** direction defaults to desc whatever the sort (switching to Name opens Z-A until toggled); status sort asc = hidden first; ties are newest first. RSVPs got only Date and Name sorting and no status filter (the owner listed fields for wishes only), and the RSVP list is not paginated (the "replaced" marks and the summary need the whole list; it sorts in Go after computing them).
- **Name sort ignores case and Vietnamese tones** (custom SQLite collation `NAME_FOLD`, `store.go`; `Ánh` sorts with `Anh`, not after `Zoe`; SQLite's NOCASE only folds ASCII). It sorts the whole string, not by given name (last word), which a Vietnamese guest list might prefer; not asked.
- **Admin list = infinite scroll + virtualization** with `@tanstack/react-virtual` (3.14.26, exact pin). Pages of 30 load only for rows in range. After hide/show/delete the loaded pages are refetched and swapped in at once (not patched locally) because filter, order and counts all depend on the status.
- **Admin page does not scroll (owner):** `main` is `h-dvh` and the list scrolls inside its own box (element virtualizer). RSVPs got the same layout; there the per-place lines and the "latest response counts" note scroll with the list so the fixed part stays small on a phone.
- **Memory report (owner):** the owner saw DOM nodes climb by tens of thousands while scrolling. Measured (Playwright, CDP, forced GC): nothing is retained, nodes and heap return to baseline (about 350 nodes, 4.2 MB); what grew was detached nodes waiting for GC, about 15 per row scrolled past. Fix: row elements are recycled through `lib/useRowSlots.ts` (a row leaving the window frees its slot, a row entering takes one; the slot is the React key), the virtualizer options are stable functions, and a placeholder has the same elements as a loaded row. Detached nodes before GC fell from about 1700 to about 550 in the same test. The owner re-tested and no longer sees it. Gotcha: keying by `index % N` does NOT recycle anything.
- **Guestbook virtualized (owner, 2026-11-22).** The public list had a "Load more" button and a growing scroll bar. The public API now also returns `total` and accepts `offset`, so the list is full length from the start and any part can load (`lib/usePagedRows.ts`, shared with the admin Wishes list). `before` and `hasMore` still work so an older cached page does not break; remove them later. Trade-off accepted: with offset paging, a wish posted by someone else while a guest scrolls shifts positions by one (a row can repeat or be skipped at a page border). The `guestbook.loadMore` copy string is unused now. Cost: the public first load grew from 808 KB to 844 KB raw and from 328 KB to 339 KB gzip (the virtualizer); lazy-loading the list after the cover opens would take most of it back (not done, no budget set).
- **Skeleton instead of loading text (owner):** the guestbook shows skeleton cards instead of "Đang tải lời chúc", with one bar per line, not a block: the name plus two message lines (the owner means "2 lines" of content, 3 lines in all; my first version had only one message line), and a bar for the date at the right of the name line (also added after the owner pointed out the missing date).
